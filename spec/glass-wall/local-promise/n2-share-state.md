## 문제

지금은 벽 내용을 다 올리기 전에 "공유 중"이 된다.

공유 시작은 서버 행과 초대 토큰을 만든 직후 상태를 shared로 바꾼다. 벽 내용은 그 뒤 동기화 연결로 올라간다. 그래서 올리다 끊기면 배지는 공유 중인데 서버에는 빈 벽만 있다.

## 목표

벽 하나의 공유 상태가 spec 상태 모델의 네 값 중 하나로 읽힌다. "공유 중"은 서버가 벽 내용을 받은 것을 확인한 뒤에만 된다. 로그인이나 업로드가 실패하면 서버 행 없이 "이 기기에만"으로 돌아온다.

## 확정 결정

- D6 = A. 서버 저장을 확인한 뒤에만 공유 중이다. 그 사이는 올리는 중이다.
- D5 = A. 로그아웃해도 공유 벽 사본은 남는다. 이 상태를 "공유 중이지만 로그아웃"으로 읽는다.

## 상태 모델 (spec에서 옮김)

| 상태 | 서버 행 | 동기화 연결 |
|---|---|---|
| 이 기기에만 | 없음 | 없음 |
| 올리는 중 | 만드는 중 | 업로드용만 |
| 공유 중 | 있음 | 있음 |
| 공유 중이지만 로그아웃 | 있음 | 없음 |

불가능한 조합 셋: 이 기기에만인데 동기화 연결이 열림, 공유 중인데 서버 행 없음, 로그인한 적 없이 공유 중.

## 담당 행 메모

| 행 | 이 노드가 맡는 부분 |
|---|---|
| T6 | 로그인 없이 쓰던 벽 내용이 그대로 올라간 뒤에 공유 중이 된다 |
| T8 | 로그인을 끝내지 못하면 서버 호출이 없고 상태는 이 기기에만이다 |
| T9 | 업로드가 실패하면 서버 행을 지우고 이 기기에만으로 돌아온다. 다시 시도하면 처음부터 한다 |
| T13 | 공유 해제 뒤 이 기기에만이고 동기화 연결이 닫힌다 |

화면 문구는 n3·n4, 실제 화면은 n9 몫이다.

## 작업

1. 벽 하나의 상태를 네 값으로 돌려주는 선택자를 만든다. 입력은 공유 상태, 진행 중 여부, 로그인 상태다. 이름은 `wallShareState(boardId)` 같은 꼴로 둔다. n3와 n4가 이것만 읽는다.
2. 공유 시작을 순서대로 바꾼다. 로그인 확인 → 서버 행 → 벽 내용 업로드 확인 → 초대 토큰 → 공유 중. 업로드는 이미 있는 일회용 업로드 함수를 쓴다. 파일함 등록도 이 순서 안에서 한다.
3. 업로드가 실패하거나 시간이 넘으면 방금 만든 서버 행을 지운다. 지우기도 실패하면 오류를 남기고 상태는 이 기기에만으로 둔다. 진행 중 가드는 그대로 지킨다.
4. 실패 이유를 둘로 나눠 내보낸다. 로그인 실패와 공유 실패다. n4가 문구를 고른다.
5. 상태 전이를 테스트로 못 박는다. 성공, 로그인 실패, 업로드 실패, 업로드 시간 초과, 두 번 누르기, 공유 해제, 로그아웃 뒤 상태.
