# 개발 서버 실행 후 렉 진단

## 증상

`bun run dev` 후 첫 화면 `/` 컴파일이 응답하지 않고 컴퓨터가 느려진다.

## 가설과 실측

| 가설 | 실측과 판정 |
|---|---|
| 메모리 부족이 현재 렉의 원인이다 | 조사 시 memory_pressure 여유 76%. 현재 메모리 부족은 지지되지 않는다. 증상 당시 메모리는 미확인이다. |
| 개발 서버가 중복 실행 중이다 | 조사 시 next 프로세스와 3000 리스너 0개. 과거 중복 실행은 미확인이다. |
| 모든 페이지가 느리다 | 최신 로그에서 약관 페이지 첫 응답 188ms, 다음 응답 15ms. 이후 `/` 컴파일이 멈췄다. |
| 컴파일 중 자원 부하가 커졌다 | 논리 CPU 8개. 1분 load 164.44. 다음 측정 94.19. 최신 로그에 Node MallocStackLogging 경고 305건. 동시 프로세스 수를 뜻하지 않는다. |
| dev 명령이 재귀 실행된다 | package.json 실행 경로에서 재귀 명령은 발견되지 않았다. 실제 프로세스 부모 관계는 미확인이다. |
| Turbopack이나 PostCSS 작업이 폭증한다 | 저장소 루트를 쓰는 Turbopack 설정과 제한 없는 Tailwind 검색 범위를 확인했다. 워커 생성 원인과 실제 검색량은 미확인이다. |

## 판단

멈추는 단계는 `/`의 개발 컴파일이다. 자원 부하가 높았다는 증거가 있다. 정확한 원인과 수정 효과는 아직 미증명이다.

MallocStackLogging 경고만으로 메모리 누수나 재귀 프로세스를 확정하지 않는다. 서버는 SIGHUP으로 종료됐다. 조사에서 새 서버는 실행하지 않았다.

Webpack에서는 첫 화면이 멈추지 않았다. 이전 Turbopack 실행과 같은 시점의 비교는 아니다. Turbopack 내부 결함이나 당시 부하와의 인과는 미확인이다. 개발 중에는 Webpack을 쓰는 우회를 추천한다.

증거 로그는 `/private/tmp/claude-501/-Users-dongpark-moss/a254508c-dd4f-41b1-a707-583fbcd070c7/scratchpad/webpack-dev.log`다. 실험에서 만든 PID 36075, 36110, 36111만 종료했다.

서버 1개로 Webpack 개발 모드를 비교한다. 실행 전 기존 서버가 없는지 확인한다. 증상 발생 시 부모 PID와 CPU를 수집한다. 같은 `/` 요청 시간과 시스템 부하를 비교한다. 부하가 커지면 해당 실험 서버만 종료한다.

Webpack에서도 멈추면 Turbopack 단독 원인 가설을 철회한다. 실행 전 부하가 다르면 기존 실행과 성능 비율을 계산하지 않는다. Webpack에서 응답해도 정확한 내부 원인까지 확정하지 않는다.

## 기존 작업의 정정
