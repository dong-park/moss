# Verified single-host release automation

This C4 implementation is not an activation approval. The historical plan in [deployment-automation-plan.md](../spec/deployment-automation-plan.md) is preserved verbatim. The implementation lane was subsequently authorized; production installation, credentials, main integration and activation belong to the parent/operator.

`release.yml` calls all four existing CI jobs and both audit jobs, then builds three linux/amd64 images, attests their exact digests, rehearses them against the previous successful image set, attests the evidence, creates one explicit GitHub deployment and waits up to 30 minutes for its host result. A failed/skipped/cancelled/missing gate cannot publish a request. Concurrency does not cancel an active replacement. Production environment access uses `deployment: false` to avoid phantom deployment history. PR CI/audit remain separate; main enters through release.

The root-installed timer retrieves data-only deployment payloads. It checks schema v1, source main/SHA, repository/workflow/run attempt, all successful gate jobs, signed evidence and each image's GitHub attestation. Download, topology, configuration, migration baseline and rollback image checks precede writer shutdown. Dedicated credentials/board configuration is required before Docker/network preflight, and normal authenticated smoke is proven against the still-serving baseline before stopping any writer. Invalid/expired smoke credentials therefore preserve the baseline. It rechecks main immediately before stopping writers. Images are fixed digest references; it never builds, pulls source, executes requested commands, recreates Postgres, runs `compose down`, removes volumes or performs global image cleanup.

## First release without baseline provenance

The running legacy images have no registry digest and their source is not established by checkout/OCI labels. Never relabel them as main, rebuild them and call that preservation, or claim their source SHA.

1. Read only the actual three running image IDs, container bindings, mounts and network names. Read only ordered Flyway `version, checksum, success` metadata. Save a sanitized operator inventory; no user/board records. Confirm Postgres major and the existing named volumes/network. Preserve the current source checkout separately; do not pull into it.
2. Explicitly export each exact running image with `docker image save` into protected recovery storage and checksum it. **Ordering for the first release (corrected 2026-11-12):** the only image repositories are the three fixed PRIVATE packages `ghcr.io/dong-park/moss-deploy-{web,server,sync}` (`scripts/deploy/release.py` `IMAGE_REPOSITORIES`). They must exist **before** the release workflow runs. A package that this public repository's `GITHUB_TOKEN` creates inherits the repository's PUBLIC visibility ([publishing with Actions](https://docs.github.com/en/packages/managing-github-packages-using-github-actions-workflows/publishing-and-installing-a-package-with-github-actions)), and a public package can never become private again ([visibility](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility)); the earlier claim here that the first workflow push creates private packages was wrong and made `ghcr.io/dong-park/moss-{web,server,sync}` public (run `43129572380`). Those three public packages are retired: left untouched, unused, and rejected by every validator. (a) With a **one-time** personal access token, an operator pushes a minimal non-runtime seed image (no application data) to each new name, labelled `org.opencontainers.image.source=https://github.com/dong-park/moss` at creation so the package is linked to this repository (first personal-account publish is private by default), then revokes the token. (b) Verify via the packages API that each package is `private`, owned by `dong-park` and linked to repository id `1383130341` (`dong-park/moss`), and that anonymous registry reads are denied. If a package does not grant this repository Actions access, add `dong-park/moss` under *Manage Actions access* (Write). (c) Only after private is proven: publish the preserved legacy images under the same fixed new repositories with a one-time package write capability, obtain digests, then pull and verify **each digest resolves to the original image ID**. Never push a legacy baseline to any other path. (d) Every `build` job first runs `publish.py registry` with only its ephemeral `GITHUB_TOKEN` (`packages: write`, no stored publisher token): all three packages must return HTTP 200 metadata without redirect, `visibility: private`, owner `dong-park`, repository `1383130341`/`dong-park/moss`, and deny anonymous reads; anything else (missing, 401/403/404, redirect, public, mismatch, malformed, network error) fails the job **before** Docker login/build/push, and the same proof re-runs after push/attest before the image identity artifact. Whether the REST packages endpoint accepts the repository `GITHUB_TOKEN` is not stated by the REST reference (it documents classic tokens); the first `main` run proves it, or fails closed before any push; the metadata-only `registry-preflight` workflow (`packages: read`, no login/pull/push) runs the same proof on demand. Keep protected exports and local IDs; unknown source remains unknown. These manual actions are outside the timer and this implementation lane.
3. Run isolated legacy→candidate→legacy actual-image compatibility and backup/restore checks with those exact digests. The initial legacy identity check compares image IDs and public assets, records `sha: null`, and cannot establish candidate revision. Failures block activation.
4. Prepare `/etc/moss-deploy/bootstrap.json` with exactly `{images:{web,server,sync},sha:null,bootstrap:true,config_sha256}`. The fingerprint is SHA256 of sorted compact JSON of exactly `{api_url,sync_url,google_client_id,terms_version}`. Record the approved topology and Flyway fingerprint in protected `config.json`. Bootstrap verifies local digest→running image ID, topology, public configuration fingerprint and migration metadata before initializing **paused** state.
5. The operator registers a GitHub `production` deployment with `task: bootstrap`, the same baseline payload, and success only after those observations/rehearsal are reviewed. That record is an admin baseline registration, not a provenance claim. The release workflow refuses to invent its own baseline when none exists: only while **no** successful baseline exists, the rehearsal input step polls for at most 15 minutes (`BASELINE_WAIT_SECONDS=900`, capped at 900) and then fails closed. An existing but invalid baseline or a public-configuration mismatch fails immediately. Every gate still tests the exact SHA and all three images; nothing is skipped or reused from a partial run.
   If the window is missed, rerun the **entire** workflow run (*Re-run all jobs*). *Re-run failed jobs* is unsupported: the host verifies every gate job of one exact run attempt and the evidence artifact of that attempt, so a partial attempt can never produce a deployable request. The same applies to any later failed release run.
6. Package/install the reviewed host policy and smoke runtime (`scripts/deploy/smoke.package.mjs` emits a real archive outside the checkout; pass it as the second argument to `install.sh`), run bootstrap and a real read-only `dry-run`, independently review the exact code/evidence, then explicitly enable the timer. The deployment request's SHA/target and parent production activation scope must be confirmed.

Do not upgrade or recreate Postgres. `compose.runtime.yml` declares it only so backup commands can address the existing service. Every app startup uses explicit app services with `--no-deps --no-build --pull never`. External volumes/network prevent implicit replacement.

## Administrative commands

Run from an administrator terminal; never type secret values into command history.

```sh
python3 /opt/moss-deploy/scripts/deploy/agent.py bootstrap
python3 /opt/moss-deploy/scripts/deploy/agent.py dry-run
python3 /opt/moss-deploy/scripts/deploy/agent.py status
python3 /opt/moss-deploy/scripts/deploy/agent.py resume
systemctl enable --now moss-deploy.timer
```

`pause` and `status` read only the protected policy and journal: they keep working with an expired GitHub token or low disk (configuration/journal ownership is still enforced). Every command that reads GitHub, drives Docker or re-enables automation (`poll`, `dry-run`, `resume`, `bootstrap`, `reconcile`, `control.py`) runs the full credential/disk preflight first. `status` also shows the outbox (`reports`, each with `delivery` failures/last error) and `undeliverable` results.

`dry-run` validates the latest request, trusted run, attested evidence, local baseline, public configuration, topology and migration state, but does not pull/start/stop containers or modify state. Images' attestations/pulls happen in the regular preflight before shutdown. Missing credentials and offline GitHub fail closed.

```sh
python3 /opt/moss-deploy/scripts/deploy/agent.py pause
python3 /opt/moss-deploy/scripts/deploy/agent.py reconcile ERROR_ATTEMPT_ID
python3 /opt/moss-deploy/scripts/deploy/control.py retry EXISTING_DEPLOYMENT_ID
python3 /opt/moss-deploy/scripts/deploy/control.py rollback-previous
```

Timer and operator commands share one nonblocking file lock. An operator command never waits for it: while the timer (or another operator) holds it, `agent.py` and `control.py` print a fixed `moss-deploy busy … nothing was changed` message and exit **75** without touching the journal; only the timer's own `poll` treats contention as a quiet exit 0. So `pause` is not queued: if it reports busy, retry it until it exits 0. A successful pause blocks the **next** replacement; it never interrupts one already running. Other exit codes: 0 done, 1 failed closed with a one-line safe reason (for example `operator files must be root owned, …`). Retry creates a fresh deployment ID for an existing verified request only when its SHA is still main and its rehearsed baseline remains current; it cannot accept an arbitrary tag/SHA. Rollback accepts no target: it verifies signed current-release compatibility evidence, recorded previous images, live migration state and exact running identities, stops writers, backs up current data, restores the previous **app images**, performs smoke, and leaves automation paused. It never restores a database. Rollback history reports the requested target, the observed running state and a distinct rollback result, separate from the original release failure. Rollback uses the verified evidence retained in the root journal at deployment time, so it no longer depends on the 90-day artifact retention; that copy must still hash to the recorded release's signed digest. GitHub must still be reachable: rollback creates its own deployment record and re-verifies the previous images' attestations (none for the legacy bootstrap images). Without GitHub, use the manual app-image restore below; there is no offline or unsigned bypass.

The atomically replaced, fsynced state journal preserves attempts and pending GitHub result reports. The terminal attempt, the new current/previous release, its outbox entry and the cleared active marker are written in **one** journal replacement, so a crash leaves either the old or the new state and never halts an already committed healthy release. Each result records the **observed** state: `serving` with the running SHA (or `legacy-bootstrap`), `stopped` (every writer stopped) or `unverified` (stopping failed), the last verified baseline, and `rollback` = `not_attempted` / `succeeded` / `failed`. GitHub statuses carry the same text, never the requested SHA as the running one. A repeated deployment ID never reapplies. Invalid request data (for example a non-object payload) is a terminal failure recorded before any Docker action. Delivery failures stay in the durable outbox with their error and make the run exit non-zero, but no longer block later valid requests; GitHub answers 404/410/422 move the entry to `undeliverable` (kept, visible, never reported as delivered). A request job may then show UNVERIFIED after its 30-minute wait; the host journal remains the source of truth. A crash/reboot during replacement stops writers and records intervention rather than guessing migration safety. Requests that fail are terminal; the timer never retries them every minute. Do not delete state to force a retry.

## Backup, failure and recovery

Web, then sync, then server stop sequentially. Sync must exit 0 after persistence; web/server may exit 0 or graceful SIGTERM 143. OOM/forced kill or failed sync persistence requires intervention. Only once writers are stopped does the deployer take a custom-format DB dump from the still-running Postgres and archive the existing attachment volume through a read-only, networkless helper using the preserved server image. Backup files are private. The existing online cron script is unchanged and retains its retention policy; it is not used as a consistent deployment recovery point because its attachment tar requires a running server and its DB/files can represent different times. Deployment backup directories have separate retention; preserve at least the latest recovery point and prune only via reviewed operator policy.

A backup failure restarts the preserved app set without starting the candidate. **Strict cutover limit:** the candidate server start, including Flyway, has 660 seconds (`SERVER_START_SECONDS`, passed as `compose up --wait-timeout`; the image healthcheck's 600 s start period keeps a slow migration from being declared unhealthy earlier). The compose subprocess itself gets that budget plus a 90 s orchestration grace (750 s; sync/web 120 s + 90 s), so the deployer's own deadline never cuts the wait short. A failed or timed-out candidate server start is UNKNOWN SCHEMA even when the history rows still equal the baseline: Postgres rolls back an interrupted transactional migration, but non-transactional statements can be partial. Writers are stopped (which interrupts a still-running migration), the attempt is `error`, automation pauses, and the previous app set is **not** restarted automatically. The deployer never terminates a migration and then declares the database safe. Migrations that cannot finish well inside the budget must be split into expand steps; long data backfills belong outside the deploy cutover. After candidate startup, actual Flyway history must equal a rehearsed successful baseline/candidate history. Unknown history, checksum divergence, partial/failed migration or inability to stop writers leaves writers stopped, records `error`, pauses automation and requires manual intervention. Only after the candidate server became ready and its history was proven compatible may a later client/smoke failure restore the previous image set, which must pass normal smoke. Legacy images have no Docker healthcheck; before any smoke (which writes to the dedicated board) the deployer waits up to 120 seconds for HTTP answers on the fixed loopback routes. It retries only that read-only probe, never the smoke. The original release still reports failure and the actual running SHA/rollback result. An app rollback is never a DB rollback.

Database restoration is deliberately manual. Pause automation, stop writers, preserve current data first, identify the backup's timestamp and user-write loss window, rehearse restoration into an isolated **new** database/attachment volume and verify authenticated fixtures, then obtain explicit operations authorization for restoring production. Never restore automatically after migration failure. After an `error`, `resume` refuses until each error attempt is reconciled. Supported procedure: keep the timer paused; inspect `status` (observed state, rollback result, phases) and the backup; repair manually (typically restart the recorded **current** app set with the installed Compose file and explicit services `--no-deps --no-build --pull never`, or follow the database procedure above); then run `agent.py reconcile ATTEMPT_ID`. Reconcile is read-only: it verifies the approved topology, that all three running containers use exactly the journal's current image IDs, that the live Flyway history hashes to the history recorded for that release (bootstrap fingerprint, or the history observed at its successful deployment/rollback) and normal authenticated smoke. Only then is the attempt marked reconciled; automation stays paused until `resume`. Reconcile accepts the history recorded for the current release or, for an attempt that carries a migration proof (next section), exactly that attempt's proven history. Any other database history (for example a partially applied or failed candidate migration) cannot be reconciled to the old release; that needs the manual database procedure and an independently reviewed new release. There is no force-safe switch, and hand-editing the journal is unsupported.

Public configuration changes (for example a terms-version bump) are not deployable by payload: release, rollback and smoke all require the GitHub Environment variables, `config.json` `public_config`, the server environment and the baseline fingerprint to match. A change requires a reviewed reconciliation: pause, update the protected host configuration and app environment together, and rebuild/re-register through a fully rehearsed release. Rollback across a configuration change is unsupported.

Deployment backups (`/var/backups/moss-deploy/<deployment id>`) are never deleted automatically. Each holds a full DB dump and attachment archive (observed production size at planning time: DB 8.9 MB, attachments 1.7 MB). Preflight refuses to start a replacement below `minimum_free_bytes`. Pruning is a manual operator action: keep at least the latest successful recovery point and any backup referenced by an unreconciled attempt, copy what is needed off-host first, and never touch the live volumes or the existing cron backups.

## Migration history after a rollback

An automatic or operator rollback restores **app images only**. When the failed release's migration set was already applied (its server became ready and its history was proven to be exactly the rehearsed candidate history), the database keeps those migrations. The old app keeps working because the rehearsal proved previous→candidate→previous on that history, and Flyway ignores applied *future* migrations; a real-image probe restarted the legacy images on such a database. After the rollback the deployer re-reads the live history; it must still be exactly a rehearsed history of that release, and its digest replaces the recorded `current_migrations_sha256` in the same atomic commit. Otherwise the result is `error`, writers stop and automation pauses.

A later release passes preflight only when the live history is **exactly** its signed rehearsal baseline **or exactly** its signed candidate history. Prefixes, subsets, histories that differ only in checksums or success flags, and extra unrehearsed migrations are refused. Supported recovery after such a rollback: first ship a retry or fix-forward with the **same migration set** (its candidate history equals the live one), and add further migrations only after that release succeeds. A fix-forward that also adds another migration is rejected in preflight with `live migration history is neither the rehearsed baseline nor candidate`, because the live intermediate history was never rehearsed for it. Blanket prefix compatibility is deliberately unsupported without its own independently rehearsed proof.

**Failed rollback or crash after a proven candidate migration.** Once the candidate server is ready and its live history is exactly a signed rehearsed history, the agent journals a *migration proof* in the same atomic write that enters the `clients` phase. The proof holds the history digest, whether it matched the rehearsed `candidate` or `baseline`, the requested SHA, the verified evidence digest and the current baseline images. If the restored app set then fails (for example a transient public-route fault that also fails its smoke), or the host crashes in `clients`/`smoke`/`rollback`, the `error` attempt keeps that proof. Supported recovery, with automation still paused:
1. Inspect `status` (the attempt's `failure`, `rollback` and `proven_history`).
2. Restart the journal's **current** app set with the installed Compose file and explicit services (`--no-deps --no-build --pull never`). Do not touch the database.
3. Run `agent.py reconcile ATTEMPT_ID`. It accepts the recorded current history or that attempt's proven history, but only while the proof is well formed, names this attempt's requested SHA, was recorded in `clients`/`smoke`/`rollback`, and is bound to the images that are still the current release. It still independently verifies the approved topology, the exact current image IDs running, the real metadata and authenticated smoke. It then stores the verified history as the current release's history.
4. `resume` explicitly.

Nothing in this path resumes automatically, changes images or touches the database. No proof is ever recorded for a failed or timed-out candidate **server** start, a crash before the proof was journaled, a history that moved after the proof, or a different attempt or baseline. Each of these still needs the manual database procedure.

## Failure diagnostics

Each terminal attempt and its outbox entry carry `failure`: the `phase` plus either `code: rejected` with the fixed, code-authored rejection reason (configuration ownership, token expiry, disk, topology, migration history, attestation, …) or `code: error` with only the exception class. Interrupted attempts record `code: interrupted`; a failed recovery adds `rollback` or `recovery`. Child-process output, exception messages, argv, paths, tokens and personal data are never journaled or printed; a rejection text containing anything but plain characters is replaced by `unprintable rejection`. GitHub statuses keep the observed-state text only.

## Manual (unversioned) builds

`docker-compose.yml` and `docker-compose.prod.yml` keep their existing build/start/recovery commands (for example `docker compose -f docker-compose.prod.yml up -d --build web server`). They pass no `BUILD_SHA`, so the images are explicitly **unversioned**: no identity file is written, `/api/deployment` and both internal readiness endpoints answer `{"status":"unversioned"}` only while neither a build SHA nor `RELEASE_SHA` exists, and their healthchecks accept exactly that. Such an image never claims a source SHA, cannot satisfy the deployer (it requires the exact release SHA, OCI labels and attestations), and setting `RELEASE_SHA` on it makes it not ready. The release workflow always builds with the exact 40-hex event SHA; an explicit invalid value fails the build. Do not invent a SHA for manual builds.

Residual (documented, not changed in this slice): `moss-deploy.service` uses `TimeoutStartSec=45min`, not a sum of the internal per-step caps. A pathological run that hits several caps can be killed by systemd; the next poll then recovers it as an interrupted `error` (fail-closed, paused).

Residual (measured, not optimized in this slice): the server healthcheck starts a JVM every 10 s, about 0.73 s wall time per probe on the dongpark host (median of 6), and the server re-validates Flyway on each probe. Lightweight JVM flags (`TieredStopAtLevel=1`, serial GC, no perf data) measured 0.69 s, a 6 % gain that does not justify an image change and its full re-rehearsal now.
