# Verified single-host release automation

This C4 implementation is not an activation approval. The historical plan in [deployment-automation-plan.md](../spec/deployment-automation-plan.md) is preserved verbatim. The implementation lane was subsequently authorized; production installation, credentials, main integration and activation belong to the parent/operator.

`release.yml` calls all four existing CI jobs and both audit jobs, then builds three linux/amd64 images, attests their exact digests, rehearses them against the previous successful image set, attests the evidence, creates one explicit GitHub deployment and waits up to 30 minutes for its host result. A failed/skipped/cancelled/missing gate cannot publish a request. Concurrency does not cancel an active replacement. Production environment access uses `deployment: false` to avoid phantom deployment history. PR CI/audit remain separate; main enters through release.

The root-installed timer retrieves data-only deployment payloads. It checks schema v1, source main/SHA, repository/workflow/run attempt, all successful gate jobs, signed evidence and each image's GitHub attestation. Download, topology, configuration, migration baseline and rollback image checks precede writer shutdown. Dedicated credentials/board configuration is required before Docker/network preflight, and normal authenticated smoke is proven against the still-serving baseline before stopping any writer. Invalid/expired smoke credentials therefore preserve the baseline. It rechecks main immediately before stopping writers. Images are fixed digest references; it never builds, pulls source, executes requested commands, recreates Postgres, runs `compose down`, removes volumes or performs global image cleanup.

## Operator inputs and prerequisites

Prepare values through the secret handoff/manager, never chat, logs or a committed file. The example JSON deliberately contains invalid nulls; it is documentation and cannot activate deployment.

- GitHub production environment: restrict to main, no mandatory per-release approval, public variables `NEXT_PUBLIC_MOSS_API_URL`, `NEXT_PUBLIC_MOSS_SYNC_URL`, `NEXT_PUBLIC_GOOGLE_CLIENT_ID`, `NEXT_PUBLIC_MOSS_TERMS_VERSION`. All four are required. API must be https and sync wss. Server runtime `PUBLIC_BASE_URL`, `GOOGLE_CLIENT_ID`, `MOSS_TERMS_VERSION` must match.
- Repository `NVD_API_KEY` for the reused audit workflow. No inherited secret set is passed.
- GitHub-hosted build/rehearsal/request jobs; no production runner. Private-repository GitHub attestations require Enterprise Cloud according to the official documentation. Do not disable provenance when unavailable.
- Choose `auth_mode: token` with a fine-grained PAT restricted to `dong-park/moss` (contents/actions read, deployments write, and attestation read when required by the private attestation endpoint), or `auth_mode: app` with a dedicated GitHub App installed on this repository only: contents/actions/attestations read, deployments write, metadata read. For App mode, configure App ID, installation ID and a root-readable private key. For scoped-token mode, put the token in a separate root-owned 0600 `token_file` and set the administrator-verified `token_expires_at` Unix timestamp. A token within 60 seconds of expiry fails closed; replacement file contents are reloaded on every API request. Renew before expiry, atomically replace the protected file, and update the protected expiry metadata. Never use the desktop gh OAuth token on production. No browser login on the host is required. The agent mints short-lived installation tokens and refreshes them; no token is printed or stored in state.
- Private GHCR read-only credential in root's isolated `DOCKER_CONFIG`. GitHub App installation tokens are not substituted for GHCR download authorization. Keep `packages:write`, `id-token:write`, `attestations:write` confined to producing jobs; host has no package write permission.
- Docker 27+/Compose 2.29+, Python 3.12+, OpenSSL, Bun 1.3.14 and a current GitHub CLI supporting `attestation verify`, `--source-digest`, `--signer-digest`, `--source-ref`, `--deny-self-hosted-runners`. The host's observed gh 2.45.0 is too old; the installer stages checksum-pinned gh 2.103.3 and Bun 1.3.14 under `/opt/moss-deploy/bin`, and checks every required provenance flag. `python3 scripts/deploy/install-tools.py --check` verifies downloads/flags in a disposable directory without installation. Archive extraction selects only the known binary member; it does not execute a remote installer or read the desktop gh configuration. Runtime attestation always invokes that dedicated CLI and isolates `GH_CONFIG_DIR`. The production Postgres container/image/major remains unchanged.
- Dedicated normal password-login account and owned board for smoke. Missing credentials block success; no JWT minting/bypass endpoint. Supply protected credentials/config; the installed smoke hashes assets extracted from the exact running web image and compares public HTML references and bytes. Operator-provided asset hashes are rejected. See [rehearsal](rehearsal/README.md).
- Existing deployment app environment copied through the secret manager into `/etc/moss-deploy/app.env`, mode 0600, root owned. Preserve all existing operational values. Do not dump environment variables or Docker Config.Env to inspect it.

All files in `/opt/moss-deploy`, `/etc/moss-deploy` and state must be owned by root and protected from other writers. Docker socket access is administrator authority. `systemd` hardening does not sandbox that authority. The fixed runtime Compose preserves project `moss`, network `moss_default`, volumes `moss_pgdata`/`moss_filedata`, and loopback ports 3001/8080/1234. The approved topology also seals the exact existing Postgres image ID; unexpected DB image changes fail preflight. Compare the exact approved topology before installation; a different topology requires reviewed policy, not payload parameters.

## First release without baseline provenance

The running legacy images have no registry digest and their source is not established by checkout/OCI labels. Never relabel them as main, rebuild them and call that preservation, or claim their source SHA.

1. Read only the actual three running image IDs, container bindings, mounts and network names. Read only ordered Flyway `version, checksum, success` metadata. Save a sanitized operator inventory; no user/board records. Confirm Postgres major and the existing named volumes/network. Preserve the current source checkout separately; do not pull into it.
2. Explicitly export each exact running image with `docker image save` into protected recovery storage and checksum it. **Ordering for the first release:** after the reviewed merge, the release workflow's `build` job pushes the three candidate images first; that creates the private `moss-{web,server,sync}` GHCR packages linked to this repository, so the workflow's `GITHUB_TOKEN` keeps write (build) and read (rehearsal) access. Packages created by hand before that may not grant the repository Actions access: in each package's settings use *Manage Actions access* to add `dong-park/moss` (Write) or delete the empty hand-made package before the first run. While the `rehearsal` job waits (step 5), an operator with a one-time package write capability publishes the preserved images under the fixed `ghcr.io/dong-park/moss-{web,server,sync}` repositories, obtains digests, then pulls and verifies **each digest resolves to the original image ID**. Keep protected exports and local IDs; unknown source remains unknown. These manual actions are outside the timer and this implementation lane.
3. Run isolated legacy→candidate→legacy actual-image compatibility and backup/restore checks with those exact digests. The initial legacy identity check compares image IDs and public assets, records `sha: null`, and cannot establish candidate revision. Failures block activation.
4. Prepare `/etc/moss-deploy/bootstrap.json` with exactly `{images:{web,server,sync},sha:null,bootstrap:true,config_sha256}`. The fingerprint is SHA256 of sorted compact JSON of exactly `{api_url,sync_url,google_client_id,terms_version}`. Record the approved topology and Flyway fingerprint in protected `config.json`. Bootstrap verifies local digest→running image ID, topology, public configuration fingerprint and migration metadata before initializing **paused** state.
5. The operator registers a GitHub `production` deployment with `task: bootstrap`, the same baseline payload, and success only after those observations/rehearsal are reviewed. That record is an admin baseline registration, not a provenance claim. The release workflow refuses to invent its own baseline when none exists: only while **no** successful baseline exists, the rehearsal input step polls for at most 15 minutes (`BASELINE_WAIT_SECONDS=900`, capped at 900) and then fails closed. An existing but invalid baseline or a public-configuration mismatch fails immediately. Every gate still tests the exact SHA and all three images; nothing is skipped or reused from a partial run.
   If the window is missed, rerun the **entire** workflow run (*Re-run all jobs*). *Re-run failed jobs* is unsupported: the host verifies every gate job of one exact run attempt and the evidence artifact of that attempt, so a partial attempt can never produce a deployable request. The same applies to any later failed release run.
6. Package/install the reviewed host policy and smoke runtime (`scripts/deploy/smoke.package.mjs` emits a real archive outside the checkout; pass it as the second argument to `install.sh`), run bootstrap and a real read-only `dry-run`, independently review the exact code/evidence, then explicitly enable the timer. The deployment request's SHA/target and parent production activation scope must be confirmed.

Do not upgrade or recreate Postgres. `compose.runtime.yml` declares it only so backup commands can address the existing service. Every app startup uses explicit app services with `--no-deps --no-build --pull never`. External volumes/network prevent implicit replacement.

## Administrative commands

Run from an administrator terminal; never type secret values into command history.

```sh
python3 /opt/moss-deploy/scripts/deploy/agent.py bootstrap
python3 /opt/moss-deploy/scripts/deploy/agent.py dry-run
python3 /opt/moss-deploy/scripts/deploy/agent.py status
python3 /opt/moss-deploy/scripts/deploy/agent.py resume
systemctl enable --now moss-deploy.timer
```

`pause` and `status` read only the protected policy and journal: they keep working with an expired GitHub token or low disk (configuration/journal ownership is still enforced). Every command that reads GitHub, drives Docker or re-enables automation (`poll`, `dry-run`, `resume`, `bootstrap`, `reconcile`, `control.py`) runs the full credential/disk preflight first. `status` also shows the outbox (`reports`, each with `delivery` failures/last error) and `undeliverable` results.

`dry-run` validates the latest request, trusted run, attested evidence, local baseline, public configuration, topology and migration state, but does not pull/start/stop containers or modify state. Images' attestations/pulls happen in the regular preflight before shutdown. Missing credentials and offline GitHub fail closed.

```sh
python3 /opt/moss-deploy/scripts/deploy/agent.py pause
python3 /opt/moss-deploy/scripts/deploy/agent.py reconcile ERROR_ATTEMPT_ID
python3 /opt/moss-deploy/scripts/deploy/control.py retry EXISTING_DEPLOYMENT_ID
python3 /opt/moss-deploy/scripts/deploy/control.py rollback-previous
```

Timer and operator commands share one nonblocking file lock. Pause takes effect between replacements. Retry creates a fresh deployment ID for an existing verified request only when its SHA is still main and its rehearsed baseline remains current; it cannot accept an arbitrary tag/SHA. Rollback accepts no target: it verifies signed current-release compatibility evidence, recorded previous images, live migration state and exact running identities, stops writers, backs up current data, restores the previous **app images**, performs smoke, and leaves automation paused. It never restores a database. Rollback history reports the requested target, the observed running state and a distinct rollback result, separate from the original release failure. Rollback uses the verified evidence retained in the root journal at deployment time, so it no longer depends on the 90-day artifact retention; that copy must still hash to the recorded release's signed digest. GitHub must still be reachable: rollback creates its own deployment record and re-verifies the previous images' attestations (none for the legacy bootstrap images). Without GitHub, use the manual app-image restore below; there is no offline or unsigned bypass.

The atomically replaced, fsynced state journal preserves attempts and pending GitHub result reports. The terminal attempt, the new current/previous release, its outbox entry and the cleared active marker are written in **one** journal replacement, so a crash leaves either the old or the new state and never halts an already committed healthy release. Each result records the **observed** state: `serving` with the running SHA (or `legacy-bootstrap`), `stopped` (every writer stopped) or `unverified` (stopping failed), the last verified baseline, and `rollback` = `not_attempted` / `succeeded` / `failed`. GitHub statuses carry the same text, never the requested SHA as the running one. A repeated deployment ID never reapplies. Invalid request data (for example a non-object payload) is a terminal failure recorded before any Docker action. Delivery failures stay in the durable outbox with their error and make the run exit non-zero, but no longer block later valid requests; GitHub answers 404/410/422 move the entry to `undeliverable` (kept, visible, never reported as delivered). A request job may then show UNVERIFIED after its 30-minute wait; the host journal remains the source of truth. A crash/reboot during replacement stops writers and records intervention rather than guessing migration safety. Requests that fail are terminal; the timer never retries them every minute. Do not delete state to force a retry.

## Backup, failure and recovery

Web, then sync, then server stop sequentially. Sync must exit 0 after persistence; web/server may exit 0 or graceful SIGTERM 143. OOM/forced kill or failed sync persistence requires intervention. Only once writers are stopped does the deployer take a custom-format DB dump from the still-running Postgres and archive the existing attachment volume through a read-only, networkless helper using the preserved server image. Backup files are private. The existing online cron script is unchanged and retains its retention policy; it is not used as a consistent deployment recovery point because its attachment tar requires a running server and its DB/files can represent different times. Deployment backup directories have separate retention; preserve at least the latest recovery point and prune only via reviewed operator policy.

A backup failure restarts the preserved app set without starting the candidate. **Strict cutover limit:** the candidate server start, including Flyway, has 660 seconds (`SERVER_START_SECONDS`; the image healthcheck's 600 s start period keeps a slow migration from being declared unhealthy earlier). A failed or timed-out candidate server start is UNKNOWN SCHEMA even when the history rows still equal the baseline: Postgres rolls back an interrupted transactional migration, but non-transactional statements can be partial. Writers are stopped (which interrupts a still-running migration), the attempt is `error`, automation pauses, and the previous app set is **not** restarted automatically. The deployer never terminates a migration and then declares the database safe. Migrations that cannot finish well inside the budget must be split into expand steps; long data backfills belong outside the deploy cutover. After candidate startup, actual Flyway history must equal a rehearsed successful baseline/candidate history. Unknown history, checksum divergence, partial/failed migration or inability to stop writers leaves writers stopped, records `error`, pauses automation and requires manual intervention. Only after the candidate server became ready and its history was proven compatible may a later client/smoke failure restore the previous image set, which must pass normal smoke. Legacy images have no Docker healthcheck; before any smoke (which writes to the dedicated board) the deployer waits up to 120 seconds for HTTP answers on the fixed loopback routes. It retries only that read-only probe, never the smoke. The original release still reports failure and the actual running SHA/rollback result. An app rollback is never a DB rollback.

Database restoration is deliberately manual. Pause automation, stop writers, preserve current data first, identify the backup's timestamp and user-write loss window, rehearse restoration into an isolated **new** database/attachment volume and verify authenticated fixtures, then obtain explicit operations authorization for restoring production. Never restore automatically after migration failure. After an `error`, `resume` refuses until each error attempt is reconciled. Supported procedure: keep the timer paused; inspect `status` (observed state, rollback result, phases) and the backup; repair manually (typically restart the recorded **current** app set with the installed Compose file and explicit services `--no-deps --no-build --pull never`, or follow the database procedure above); then run `agent.py reconcile ATTEMPT_ID`. Reconcile is read-only: it verifies the approved topology, that all three running containers use exactly the journal's current image IDs, that the live Flyway history hashes to the history recorded for that release (bootstrap fingerprint, or the history observed at its successful deployment/rollback) and normal authenticated smoke. Only then is the attempt marked reconciled; automation stays paused until `resume`. A database left at a different history (for example a partially applied candidate migration) cannot be reconciled to the old release; that needs the manual database procedure and an independently reviewed new release. There is no force-safe switch, and hand-editing the journal is unsupported.

Public configuration changes (for example a terms-version bump) are not deployable by payload: release, rollback and smoke all require the GitHub Environment variables, `config.json` `public_config`, the server environment and the baseline fingerprint to match. A change requires a reviewed reconciliation: pause, update the protected host configuration and app environment together, and rebuild/re-register through a fully rehearsed release. Rollback across a configuration change is unsupported.

Deployment backups (`/var/backups/moss-deploy/<deployment id>`) are never deleted automatically. Each holds a full DB dump and attachment archive (observed production size at planning time: DB 8.9 MB, attachments 1.7 MB). Preflight refuses to start a replacement below `minimum_free_bytes`. Pruning is a manual operator action: keep at least the latest successful recovery point and any backup referenced by an unreconciled attempt, copy what is needed off-host first, and never touch the live volumes or the existing cron backups.

## Manual (unversioned) builds

`docker-compose.yml` and `docker-compose.prod.yml` keep their existing build/start/recovery commands (for example `docker compose -f docker-compose.prod.yml up -d --build web server`). They pass no `BUILD_SHA`, so the images are explicitly **unversioned**: no identity file is written, `/api/deployment` and both internal readiness endpoints answer `{"status":"unversioned"}` only while neither a build SHA nor `RELEASE_SHA` exists, and their healthchecks accept exactly that. Such an image never claims a source SHA, cannot satisfy the deployer (it requires the exact release SHA, OCI labels and attestations), and setting `RELEASE_SHA` on it makes it not ready. The release workflow always builds with the exact 40-hex event SHA; an explicit invalid value fails the build. Do not invent a SHA for manual builds.

## Verification and evidence

```sh
MOSS_DEPLOY_DOCKER_TESTS=required python3 -m unittest discover -s scripts/deploy/tests -v
python3 -m py_compile scripts/deploy/*.py
node --test deploy/rehearsal/*.test.mjs
actionlint
sh -n scripts/deploy/install.sh
```

`MOSS_DEPLOY_DOCKER_TESTS=required` makes the executor's real `docker exec`/`psql` metadata test against an owned, networkless Postgres 18 mandatory; without it, the test is skipped only where Docker is absent. CI runs it in the `ci / deploy-checks` job, which the host requires as a release gate (with `contract` in the release run). Run the repository's unchanged web typecheck/lint/test/i18n/build, server tests, sync typecheck/tests and MCP typecheck/tests using their CI-pinned tools. Full actual-image rehearsal, deployment/failed-rollout, restore, old client and migration-failure checks are mandatory beyond unit tests. Sign only evidence from completed real-image checks. Exact-head CI, independent C4 review and first production verification remain separate gates; local passing tests cannot establish them.
